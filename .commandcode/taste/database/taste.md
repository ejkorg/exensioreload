# database
- All database schema should be managed via Liquibase changelogs; if a table was created manually/out-of-band, it needs a Liquibase changeset to create it (including JPA entities on the internal datasource that previously relied on manually created tables, so a fresh PostgreSQL DB gets them). Confidence: 0.75
- Prefers additive/non-destructive migrations: when moving to a new database (e.g., Oracle → PostgreSQL), keep the existing DB profile/config working as the default/rollback path and add the new database as a separate opt-in Spring profile (e.g., `onsemi-postgresql`) instead of overwriting or deleting the old one. This extends to IDE configs (launch.json, tasks.json) — add new profile entries alongside, don't replace. Confidence: 0.94
- Before making destructive edits to uncommitted working-tree files (especially files that don't compile or have deleted live methods), investigate the damage fully, present findings, and ask the user how to proceed rather than silently rewriting — it's their in-progress work. Confidence: 0.60
- When a secondary checklist or plan document (e.g., DEAD_CODE_CLEANUP_CHECKLIST.md) is referenced, verify that the current code changes actually match what the checklist authorizes before assuming the checklist was applied. Cross-reference each item against the actual codebase with grep/read — many items may be stale (already done), incorrectly labeled, or not actually dead. Confidence: 0.80
- When a codebase supports multiple databases via profiles, SQL dialect helpers (metadata queries, sequence/id expressions, date-truncation, ALTER TABLE DDL) must have explicit per-database branches (isOracle/isPostgres) rather than relying on a shared H2-compatible fallback — H2 constructs like FORMATDATETIME, NEXT VALUE FOR, ALTER COLUMN ... SET, and ADD (...) break on PostgreSQL. Confidence: 0.70
- Migration scope: when migrating only the internal datasource to PostgreSQL, keep the external/site database layer (dbconnections.yml) untouched and out of scope. Confidence: 0.70
