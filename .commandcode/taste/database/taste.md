# database
- All database schema should be managed via Liquibase changelogs; if a table was created manually/out-of-band, it needs a Liquibase changeset to create it (including JPA entities on the internal datasource that previously relied on manually created tables, so a fresh PostgreSQL DB gets them). Confidence: 0.75
- Prefers additive/non-destructive migrations: when moving to a new database (e.g., Oracle → PostgreSQL), keep the existing DB profile/config working as the default/rollback path and add the new database as a separate opt-in Spring profile (e.g., `onsemi-postgresql`) instead of overwriting or deleting the old one. This extends to IDE configs (launch.json, tasks.json) — add new profile entries alongside, don't replace. Confidence: 0.94
- Before making destructive edits to uncommitted working-tree files (especially files that don't compile or have deleted live methods), investigate the damage fully, present findings, and ask the user how to proceed rather than silently rewriting — it's their in-progress work. Confidence: 0.60
- When a secondary checklist or plan document (e.g., DEAD_CODE_CLEANUP_CHECKLIST.md) is referenced, verify that the current code changes actually match what the checklist authorizes before assuming the checklist was applied. Cross-reference each item against the actual codebase with grep/read — many items may be stale (already done), incorrectly labeled, or not actually dead. Confidence: 0.80
- When a codebase supports multiple databases via profiles, SQL dialect helpers (metadata queries, sequence/id expressions, date-truncation, ALTER TABLE DDL) must have explicit per-database branches (isOracle/isPostgres) rather than relying on a shared H2-compatible fallback — H2 constructs like FORMATDATETIME, NEXT VALUE FOR, ALTER COLUMN ... SET, and ADD (...) break on PostgreSQL. Confidence: 0.70
- Migration scope: when migrating only the internal datasource to PostgreSQL, keep the external/site database layer (dbconnections.yml) untouched and out of scope. Confidence: 0.70
- Liquibase changelogs are idempotent historical records — old migration steps that have already run should not be edited retroactively. Only fix live/running code (Java queries, active CHECK constraints). Confidence: 0.70
- Liquibase changesets must be cross-database portable: prefer Liquibase's built-in preconditions (`<indexExists>`, `<tableExists>`, `<columnExists>`) over `sqlCheck` against DB-specific dictionary views (e.g., Oracle's `user_ind_columns`); gate any DB-specific SQL with `<dbms type="..."/>` or `<sql dbms="..."/>` so it doesn't run on every database. Confidence: 0.85
- When a Liquibase migration fails on a newly-added target DB (e.g., PostgreSQL), sweep the entire changelog directory for other un-gated DB-specific constructs (dictionary views, `SYSTIMESTAMP`, `FROM dual`, `MERGE INTO`, sequences, PL/SQL) rather than fixing only the single reported changeset — the next failure is usually already present. Confidence: 0.75
- During a fresh migration to a new database, editing existing Liquibase changelogs to add `<dbms>` branches (preserving the original DB's behavior) is acceptable — the "don't edit already-run changelogs" rule applies to altering historical behavior, not to adding a new target DB's branch. Confidence: 0.60
- For idempotent inserts in Liquibase migrations, prefer `INSERT ... SELECT ... WHERE NOT EXISTS (...)` over `ON CONFLICT (col) DO NOTHING` when the unique constraint may not exist yet at that point in the migration (e.g., it's created in a later changeset) — PostgreSQL's `ON CONFLICT` requires an existing unique/exclusion constraint. Confidence: 0.70
- When a Liquibase changeset modifies or analyzes a table that may not exist on all target databases (e.g., a legacy/pre-existing table that changelogs only ever modify but never create), guard it with a `<tableExists tableName="..."/>` precondition using `onFail="MARK_RAN"` so it skips cleanly where the table is absent — and keep the guard consistent with sibling changesets touching the same table. Confidence: 0.75
- In Liquibase changelogs using the newer XSD, element order inside a `<changeSet>` is strict — `<preConditions>` must come before `<comment>` (and the change elements). Placing `comment` first causes a `cvc-complex-type.2.4.a` parse error. Match the ordering used by sibling changesets in the same file. Confidence: 0.70
- PostgreSQL folds unquoted identifiers to lowercase, so `INFORMATION_SCHEMA` metadata queries are case-sensitive: existence helpers (`tableExists`, `columnExists`, `sequenceExists`, `constraintExists`) must match with `toLowerCase()` on PostgreSQL, while `toUpperCase()` is only correct for Oracle (`user_*` views) and H2. Apply the casing branch consistently across all metadata-existence helpers, not just the one that failed — fixing `columnExists` alone would just surface the same bug in `tableExists`/`createTable` on the next run. Confidence: 0.75
- When a table's schema is self-managed by application code at runtime (a `createTable` DDL plus idempotent `ensure*` column helpers) rather than by Liquibase, keep the two paths in sync: any new column must be added to the `createTable` DDL (in every per-DB branch) AND to an idempotent `ensure*` check, so both fresh-created tables and pre-existing/partially-created tables (e.g., left over from a failed prior run) end up complete. Because Liquibase column changesets against a table the changelogs never create get MARK_RAN on a fresh DB, the app-side DDL/ensure code is the real source of truth — derive the required column set by scanning all SQL (SELECT/INSERT/UPDATE) that references the table, not just the first reported missing column. Confidence: 0.75
