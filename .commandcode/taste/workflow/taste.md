# workflow
- The user's environment cannot run builds or installs — java, maven, node, npm, python, perl, and git are all unavailable in the local authoring workspace. Verify fixes statically via grep/read, IDE diagnostics, and type-level reasoning rather than attempting builds, compilation, or shell commands. This restriction is LOCAL to the authoring workspace only: the production/deployment machine runs node/java and CAN `npm install`, build, and run tests, so that is where verification happens. Confidence: 0.95
- When a design spec names specific third-party libraries (e.g., chart.js, chartjs-plugin-streaming, xlsx, jspdf, html2canvas, d3), implement with those spec-intended libraries and declare them in package.json — do not substitute already-installed alternatives (e.g., echarts instead of Chart.js) merely because the local workspace can't install. The build machine will run `npm install`, and earlier spec-deviation workarounds should be reworked back to the spec approach once this is clarified. Confidence: 0.9
- Continue implementing fully even when the code cannot be compiled/run in the current workspace — don't defer or stub work that depends on unavailable installs; instead flag in the project task log exactly what must be verified (npm install / ng build / npm test) on the build machine. Confidence: 0.85
- Tracks long multi-step tasks via a markdown progress/checklist file (e.g., ORACLE_TO_POSTGRES_INTERNAL_DB_CHECKLIST.md, or .kiro/specs/<feature>/tasks.md with an Implementation Status Log) and expects work to resume from the last completed item on a terse go-ahead. A bare "continue" (possibly with the tracking file open in the IDE) means: read the log, pick up the next sensible in-scope work, and keep driving the task list to completion without asking for step-by-step instructions. Confidence: 0.87
- When working from a spec's task checklist (e.g., `.kiro/specs/<feature>/tasks.md`), the checklist itself is the monitoring mechanism: tick each completed task's `- [ ]` box to `- [x]` as soon as it is done (and keep those ticks in sync with the log section), rather than only writing prose into an implementation-status log. The user points at the checklist and expects box states to reflect actual completion. Confidence: 0.8
- Verify factual claims about the codebase against the actual code (grep/read) before asserting them; user pushes back on unverified statements (e.g., "check again" when told a table isn't created by any Liquibase changelog). Confidence: 0.75
- When the user reports specific compile/type errors and asks for a "root cause fix for all," do a comprehensive sweep (grep across the full codebase) to find every instance of the same class of issue before applying fixes — fix the root cause (e.g., missing interface fields) rather than patching individual call sites one at a time. Confidence: 0.80
- When asked to make another backend app in the same workspace match a documented standard (e.g., an API documentation file written for a sibling app), first assess what's actually applicable before applying changes — align the genuinely-applicable parts and explicitly flag/hold back anything intentionally out of scope for that app rather than forcing full parity. Confidence: 0.65
- When implementing from a spec task list for an MVP, exclude test/spec-related tasks by default ("implement the task for MVP, exclude the TEST related task"): write only the core implementation and tick only non-test checklist boxes, leaving property-spec/test subtasks unticked and documenting them as out of scope rather than stubbing them out. Confidence: 0.7
- Treat package.json as the complete provisioning manifest: when code imports a new third-party library, declare every needed entry (dependencies AND devDependencies, including matching `@types/*` packages for libraries that ship JS without bundled TS types, e.g., `@types/d3`) so a fresh `npm install` on the production/build machine downloads everything and `ng build` compiles. The user explicitly handles installs on the production server and asks only that package.json be kept install-ready rather than worrying about local installs. Confidence: 0.8
- Version pins in package.json must satisfy the peerDependency ranges of the libraries they pair with so a plain `npm install` resolves without ERESOLVE (e.g., chartjs-plugin-streaming@2.x peers with chart.js@^3, so the charting stack must be pinned coherently — chart.js@^3.9.1 + chartjs-adapter-date-fns@^2.0.0 + date-fns@^2.30.0 — rather than mixing chart.js 4 with the v2 streaming plugin). When the user reports an npm peer conflict from their own install, fix it by aligning to a stable, mutually-compatible version set (even if that means downgrading a major) instead of recommending `--force`/`--legacy-peer-deps` or adopting a beta major to keep the newer library. Confidence: 0.6
- Frontend work is validated by the user running the Angular production build (`npm run build:prod` → `ng build --configuration production`), whose strict AOT checks reject `private` members referenced from a component template (TS2341) and wrong relative import paths (TS2307, which also breaks Angular's static `imports` analysis as NG1010). Author new Angular components so template-called methods are public and import paths are computed from the component's own folder; when the user pastes such build errors, fix them and sweep sibling/new components for the same pattern before asking for a rebuild. Confidence: 0.7
- The user builds/runs from a separate copy of the repo (e.g., `Documents\work\exn-reload-wip\wip2\exensioreload\frontend`) that is NOT where edits are authored (e.g., `Desktop\wip\exensioreload\frontend`), and pastes the raw output. When pasted errors appear to contradict files the assistant already fixed, do not blindly re-fix: grep the actual edited files and compare error line numbers/content against the current source to distinguish genuine bugs from a stale/missing copy in the build folder, then either tell the user to sync the source tree into the build folder or offer to apply edits directly there. Confidence: 0.55
- The user's Angular production build output is expected to be clean of warnings, not just errors: an NG8113 warning (a component in `imports[]` that is no longer used in the template) should be fixed by removing both the import and its `imports[]` entry, and the CommonJS "optimization bailout" warnings from intentionally-used export/PDF libraries (jspdf→canvg, html2canvas, dompurify, xlsx, raf, rgbcolor, core-js) should be silenced by registering them under `build.options.allowedCommonJsDependencies` in angular.json rather than replacing or dropping the libraries. Confidence: 0.5
